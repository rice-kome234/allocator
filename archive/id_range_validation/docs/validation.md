## IDごとの排他走査と通常の整数state（2026-10-17）

`GetRange<T>(id)` がID全体の走査権を取得する構成へ変更しました。同じIDは同時に1つのRangeだけが利用でき、別IDは並列利用できます。取得はCASで一度だけ試行し、使用中なら無効なRangeを返します。Rangeは移動専用で、破棄またはReset時に解放します。名前付きRangeは範囲forの末尾やbreakでも権利を保持します。空IDの取得成功と取得失敗はbool変換で区別します。

`slab::Component::state` は通常の `int` です。Rangeの解放時のreleaseと次の取得時のacquireで、実体の更新を次の担当へ引き継ぎます。走査中の要素ごとのatomic読み取りはありません。実体はそのIDの担当だけが読み書きする利用契約で、外部の生ポインタによるアクセスや共有リソースはPoolの保護対象ではありません。ID単位の排他制御であり、方式全体はロックフリーではありません。

## 数値ID別の実体コピー・仮想予約と段階コミット（2026-10-15）

現行実装は、コピーコンストラクタで構築した実体をPoolが所有する方式です。クラス内のstatic IDは使わず、`Register<Enemy>(1, ...)` / `GetRange<Enemy>(1)` の数値で領域を選びます。公開h、テンプレート実装h、cppの3ファイル構成を維持しています。旧ポインタ保持版は `archive/pointer_pool/` へ保存し、旧ベンチマークとともに現行プロジェクトのコンパイル対象から外しました。

### 実装と契約

- `MEM_RESERVE`で仮想領域を確保し、必要な部分だけ`MEM_COMMIT`。初期個数、予約個数、コミット量、事前タッチを設定できる。ReserveとCommitも個別に呼べる。
- 型サイズとページサイズの最小公倍数で区間を揃える。同じ予約領域内では実体がsizeof(T)間隔で続き、拡張しても既存の実体を移動しない。予約超過は別予約領域を追加するため、全体の隣接性は保証しない。
- byte配列の寿命はコミット済み区間だけで開始し、各実体を一つの区間内に構築する。未コミット領域をC++配列として扱わず、個別のTをT[]として走査しない。
- 型付きコピーとデストラクタを登録し、Tのコピー・破棄にnothrowを要求。Clearは全実体を破棄して容量を保持し、Pool破棄で実体と予約を解放する。1件削除は現行APIに含めない。
- 並列追加はBeginで全容量を準備し、CASで重複しない区間を取得。コピー完了後に外部バリア/joinで同期し、Endで件数を公開する。予約・公開の件数は分離している。
- CAS区間取得はロックフリーのsize_t atomicを要求。OS操作・コピーコンストラクタ・ワーカーの完了待ちを含む全体のロックフリー性は保証しない。
- mainはコピー元のnew、コピー、コピー元の解放、範囲for、追加コミット、14ワーカーでのコピー・Update・Clearを示す。並列実行と計測はbenchmarksへ分離。

Slab Pool を未構築メモリの確保・即時返却に限定しました。型との対応、構築・破棄、遅延破棄キューは利用側が管理します。本体は `slab_pool.h` と `slab_pool.cpp` の 2 ファイルです。以前のテンプレート型登録層は削除済みです。

|---|---|

| 自動テスト | Debug・Release とも 11 / 11 グループ成功 |
| AddressSanitizer | Debug x64、11 / 11 グループ成功、検出エラーなし |
| Debug / Release の引数なし実行 | テスト・数値 ID の使用例・短縮ベンチマークの全検証成功 |
| 短縮ベンチマーク | checksum `8952982280445` |
| Provider の回収照合 | Group・Slab・索引の要求バイト残数 0、確保／解放回数一致 |
| Atomic の実行時確認 | 64 bit 整数とポインタはロックフリー。Pool 全体には Mutex がある |
| 例外構文 | C++ の本体・使用例・テスト・測定に `try / catch / throw` なし |

使用例は ID 1 / 2 の 2 グループ、確保中 2 スロット → 返却後 0 スロット、再利用用に保持する容量 192 スロットと表示します。

### キー入力による継続的な並列更新

`main.cpp` の対話テストは 4 本の常駐ワーカーを使用し、開始・完了バリアで入力処理と Update を区切ります。Debug / Release のビルドは警告なしで成功しました。各構成で「追加・拡張・一時停止・全削除・再利用・再開・Q 終了」「空の入力終端」「生存オブジェクトがある入力終端」「大文字キーと Esc 終了」の 4 ケース、計 8 ケースを入力リダイレクトで実行して成功しました。

`eb12 s.scs12 q` のケースでは、Enemy / Bullet が各 65 個、Slab が計 4 枚へ増えること、一時停止中にフレーム番号と更新回数が変わらないこと、全削除後も容量 256 を保持すること、各 64 個を再追加しても Slab が増えないこと、再開後の各先頭オブジェクトの更新回数が 1 になることを出力で照合しました。すべて終了コード 0、終了時の確保中スロット数は 0 です。

コンソールの実際のキー入力でも、Enter なしの追加・一時停止・全削除・再追加・再開・Q 終了を確認しました。入力しない間もフレームと位置が進み、一時停止中は更新が止まります。対話テストでの ASan は今回実行していません。

### 現在の測定条件と確認範囲

[benchmark-numeric-quick.txt](benchmark-numeric-quick.txt) は現在の API による Release 短縮実行ログです。要素は従来と同じ 64 バイト、比較対象は new/delete、計測値は 3 回の中央値です。ID 登録を計測前に済ませ、取得・返却の ID 検索と呼出側の構築・破棄を計測に含めます。Slab の最終的なヒープへの返却は含めません。

今回の 10,000 個の記録では、new/delete の合計 0.1978 ms、初回プール 0.4060 ms、再利用プール 0.2948 ms でした。再利用の生成単独は 0.0826 ms（new 0.1337 ms）ですが、生成から返却までの合計は new/delete の方が速い結果です。この測定は本ハーネス・本実行環境の値であり、実際のゲームや他の型の性能を保証しません。

現在の実装では走査 Iterator の処理も cpp にあります。満杯のプールでの空き探索は Slab 数に比例し、返却は ID ごとの Mutex とアドレスの二分探索を使います。型識別や返却経路の最適化を評価する場合は、実環境へ組み込んだ条件で再測定してください。

数値 ID 版の全条件（最大 100 万個）は今回実行していません。以下の過去の表と `benchmark-full.txt` / `benchmark-quick.txt` は旧 Destroy Queue 版です。即時返却に変わっているため、旧表と今回の合計時間をそのまま比較しないでください。

ASan は Slab を一つの確保領域として扱います。独自スロットの poison / unpoison は実装していないため、返却済みスロットへのアクセスをすべて検出できるわけではありません。ThreadSanitizer、メモリモデルの形式検証、ハードウェアのキャッシュミス測定は行っていません。

| 1,000 | 0.0289 | 0.0118 | 0.0111 | 0.0452 | 0.0381 | 0.0364 |
| 10,000 | 0.1350 | 0.1254 | 0.0916 | 0.2008 | 0.3923 | 0.3679 |

## メモリ使用量

100 万個・容量 100 万の Pool は **68,262,336 byte（約 65.10 MiB）**です。内訳は Slab 15,625 個 × 4,352 byte = 68,000,000 byte、索引容量 16,384 × 16 byte = 262,144 byte、Pool 本体 192 byte。

通常確保の本体要求量は 64,000,000 byte、ポインタ列は別に 8,000,000 byte。Pool + ポインタ列方式も 8,000,000 byte が追加されます。直接走査方式はその配列を必要としません。どちらの方式も CRT／OS の確保ヘッダーや断片化を含まない値で、プロセス実使用メモリではありません。

Slab を終了まで保持するため、使用率が 10% に落ちても Pool の要求量は変わりません。有効本体サイズ / Pool 要求量は 100% 使用時 **93.7559%**、10% 使用時 **9.3756%**です。

## ボトルネックと改善候補

以下は結果とコード構造からの見立てで、各要因を分離したハードウェア計測は行っていません。

- 共有 Pool は同じ cursor 付近の allocated / live ワードにアクセスが集中する。CAS 再試行とキャッシュラインの移動が候補。スレッドごとの Slab ヒントや小さな予約バッチを次の比較候補にできる。
- Destroy は Mutex と二分探索が毎回必要。破棄要求をスレッド別にまとめて取り込む API、所有 Slab 情報／世代を持つハンドルなら改善余地がある。生ポインタの安全な検査を削って高速化はしていない。
- Slab 追加時のソート索引への挿入は要素移動を伴う。大量の初回拡張には Reserve、将来的には別のアドレス索引が候補。
- Bitmap Iterator の分岐・ビット操作と Slab 間リンクは、十分に局所的なポインタ列より高コストになり得る。全生存ワードの特別処理、非空 Slab 索引、1 Slab 当たりの容量比較が候補。
- Flush はスロットごとに Atomic RMW を行う。安全なフェーズ境界を保ったまま、ワード単位にまとめる方式を追加比較できる。
- 空 Slab の回収は保持メモリを減らせるが、ポインタ寿命・確保経路の回収同期を追加設計する必要がある。今回の実装には含めない。
- SIMD／SoA／AoSoA、世代番号付きハンドル、Windows 仮想メモリ Provider は将来の拡張候補。

速度が改善しなかった条件も含めて、現状は「型別配置・安定アドレス・CAS 確保・遅延破棄・直接走査を比較できる検証実装」です。常に汎用アロケータやポインタ列より速いとは結論していません。
